这部分新增的内容不算难理解，主要是一些代码上了解。
这里新建了一个permission	Manager 专门用于给工具管理权限
首先是工具权限的审批，包括，允许，拒绝，询问。对工具权限进行了分层过滤，首先进行参数pydantic过滤，然后使用静态规则先判断，包括但不限于，操作项目文件之外的文件 不管之前有没有填写一直允许/拒绝都要询问。只有写note和读项目内文件默认放行。
需要详细说明的是ask部分的实现：
如果返回allow或deny（包括默认的deny，默认的allow 还有用户之前如果填写过一直允许或者一直拒绝 那么在这个会话中也可以复用，作为会话状态保存），比较特殊的ask的实现。需要permission	Manager先暂停当前调用，返回一个future暂停当前协程，当用户的决定通过 tui->socket->core->runner -》loop回到当前工具调用的run下，唤醒之前挂起的工具调用审批的相关协程 继续loop。

这里比较值得关注的是 审批卡片不能阻塞消息泵。这里有点绕，我们从数据端再从头捋一下。
tui发送命令“给我测试一下某某功能”-》socket client 向server发送一个command A 然后这个协程一直等待这个command返回-》server那边收到commandA后将命令发给core -》core发给agentloop和eventbus-》在agentloop的过程中，不断通过eventbus来让tui端看到最新进展 但是这个协程实际上还是等在之前的地方-》由于agentloop需要审批，因此采取event的形式，将审批做成一个event发送给client那边，然后协程暂停-》注意，这时server这边通过socket读取command命令后 同样在等这个协程的结果出来后向client返回command的结果-》client那边通过ipc收到event后将其改成具体的界面选择发送给TUI-》TUI界面点击审批结果 再次将结果通过command的形式，将审批结果通过client发送给server，我们将其称为commandB-》但是这里尴尬的事情发生了，由于上面我们说到，server分了一个协程不断按行读取commad，然后根据command执行命令，启动run和agentloop，但是由于agentloop的工具审批，这个协程停止了-》这导致 这个协程没办法往下按行读命令了！它读不到命令缓冲中的设置审批结果的commandB了-》这个协程读不到commandB，也就一直没法将permission中的future进行修改，也就导致这个协程暂停，然后接着导致协程读不到下一行命令-》这就在服务端形成了一个死循环，而客户端这边也由于一直得不到event和返回的response，画面就卡死了。

上面可以很清楚的看到 这是由于协程中读取命令和执行命令 是一个协程下的动作，所以，我们对这里进行修改即可。
在读取完命令后，重新创建一个用于执行命令的协程，将其包装成task，这样上面core的这个协程X读取命令后，新建一个协程a执行命令，由于审批这个执行命令的协程暂停，在这个过程中，原来的协程已经接着继续读下一行命令，当commandB回来后，读取后再新建一个协程b执行命令，这个协程b下 将commandB执行完毕，更新future 从而唤醒协程a ,协程a结束后返回，协程X再返回commandA的response（也即这一轮run的response）给tui。

在安全性和效果这里同样有几点思考：
1.其实目前的工具安全性的审批只是静态的，并不是在操作系统层面禁止，假如有一个py文件在项目中，然后在文件内容中写一些查阅、删除外部文件的代码，这个安全性审核是没法避免的。也即安全性审批的效果有待改正。
2。其实关于效果改正，其实之前自主规划部分的task的实现效果也是有待证明的，假如agent在某次run中制定了若干个task，但是是否完成了这些task，仍然是agent自己来判定的，这实际上不太合理，应该通过专门的reviser或者在真正的测试环境中通过运行真实的测试文件来确定完成程度，不然agent可能会瞎编，谎称自己完成了任务。
