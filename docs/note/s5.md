# S5 阶段复盘：Permission / Tool Execution 的安全边界

> 对应决策：[ADR 0007](../decisions/0007-s5-permission-tool-execution-review.md)

## 一、PermissionManager 的审批模型

新增 PermissionManager 专门管理工具权限，审批分三态：**allow / deny / ask**。工具权限经过分层过滤：

1. 先做参数 pydantic 过滤；
2. 再用静态规则判断，包括但不限于：操作项目文件之外的文件时，无论之前是否填写过「一直允许 / 一直拒绝」，都要询问；
3. 只有写 note 和读项目内文件默认放行。

`allow` / `deny` 的来源包括默认的 deny、默认的 allow，以及用户之前填写过的「一直允许 / 一直拒绝」——后者作为会话状态保存，在同一会话中可以复用。

## 二、ask 的挂起与唤醒

ask 的实现比较特殊：PermissionManager 先暂停当前调用，返回一个 future 挂起当前协程；当用户的决定经 TUI → socket → core → runner → loop 回到当前工具调用处，唤醒此前挂起的审批协程，继续 loop。

permission 相关事件无法直接发送到 TUI：需要先调用 `emit_permission`，把原始 dict 包成 Pydantic 事件，发送到 EventBus，再由 IPC broadcaster 发给 client → TUI。TUI 侧按事件类型解析为 permission block，并通过其中的 permission select 控件支持用户返回决定。返回的数据流与上面类似。

## 三、审批卡片不能阻塞消息泵

这是 S5 最绕、也最关键的一处。从数据端重新捋一遍：

1. TUI 发送命令「给我测试一下某某功能」→ socket client 向 server 发送 command A，该协程一直等待 command 返回；
2. server 收到 command A 后把命令发给 core，core 发给 AgentLoop 和 EventBus；
3. AgentLoop 过程中不断通过 EventBus 让 TUI 看到最新进展，但上述协程仍等在原处；
4. AgentLoop 需要审批，于是把审批做成 event 发给 client，协程暂停；
5. 此时 server 侧通过 socket 读取 command 的协程，同样在等该协程返回结果后才向 client 返回；
6. client 通过 IPC 收到 event 后将其渲染为界面选择发给 TUI；用户点击审批结果，结果以 command B 的形式经 client 发回 server；
7. **问题出现**：server 用一个协程不断按行读命令、并就地执行命令（启动 run 与 AgentLoop）。由于 AgentLoop 因工具审批而停止，这个协程也停止了——它无法继续往下读命令，读不到命令缓冲区里的 command B；
8. 读不到 command B，就无法修改 permission 中的 future → 协程继续暂停 → 更读不到下一行命令。

服务端由此形成死循环，客户端也因为一直等不到 event 和 response 而卡死。

### 根因与修复

根因很清楚：**读取命令和执行命令是同一个协程内的动作**。

修复方式是读取完命令后，新建一个协程来执行命令，并包装成 task：

- 协程 X 读取命令后，新建协程 a 执行命令；
- a 因审批暂停的过程中，X 已经继续去读下一行命令；
- command B 回来后，X 再新建协程 b 执行它；
- b 更新 future，唤醒协程 a；a 结束后返回，X 再把 command A 的 response（也就是这一轮 run 的 response）返回给 TUI。

## 四、对安全性与有效性的两点质疑

1. **审批只是静态的，不是操作系统层面的禁止。** 假如项目里有一个 py 文件，文件内容去查阅、删除外部文件，这种审批无法拦截。安全性审批的实际效果有待改进。

2. **task 的完成度由 agent 自己判定，不合理。** 自主规划部分让 agent 在某次 run 中制定若干 task，但是否完成仍由 agent 自己判定，它可能瞎编、谎称已完成。应当由专门的 reviser 判定，或在真实测试环境中运行真实测试文件来确定完成程度。
