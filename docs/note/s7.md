# S7 阶段复盘：Skill / Subagent / MCP 的实现缺陷盘点

> 对应决策：[ADR 0009](../decisions/0009-s7-extensible-agent-runtime-review.md)

S7 整体实现比较简陋，有非常多值得修改的地方。先记录三块的机制，再列缺陷与改进方向。

## 一、Skill

我的理解：skill 是一种相对固定的工作流，可以在工作流中调用 tool、甚至其他 skill，总之是为达成某个目的而封装好的一套流程。

实现方式：如果输入的第一个字符是斜杠，core 组建 session 时走另外一条路径——读取是否存在该 skill、读取相应参数，然后在构建 AgentLoop（主要是 ContextManager）的过程中，把提前写好的 `skill.md` 替换为对应的上下文。

如果这里能通过 HTTP 协议快速加载 skillhub 上的 skill 会更好；目前 skill 的加载仍需用户自己手动添加，比较费事。

## 二、Subagent

subagent 被做成了一个 tool，让 agent 自己决定什么时候调用、什么时候开。实际实现是在 AgentLoop 中用新的 context、新的各类参数新开一个 child AgentLoop，创建新的 EventBus，让 child EventBus 把响应 event 回传到父 EventBus，再回传给 TUI。

## 三、MCP

用 TCP 和 stdio 做了一个简单实现，分别实现 MCPClient 与 MCPServer，本地由 MCPServerManager 管理 client 对相关 server 的行为。

## 四、缺陷与改进方向

### 1. Skill

1. **只能接纯 prompt 的 skill。** 一旦某些 skill 附带代码，仍然依赖 LLM 自己去跑，并不是强制性的。
2. **`render_prompt` 的实现有 bug。** 在 `session.send_message` 中：

   ```python
   goal = self._skill_loader.render_prompt(skill, arguments)
   system_prompt_override = skill.system_prompt_template
   ```

   而 `render_prompt` 的实现是：

   ```python
   return skill.system_prompt_template.replace("$ARGUMENTS", arguments)
   ```

   Python 中字符串不可变，因此该函数并没有修改 `skill.system_prompt_template`。赋值给 `system_prompt_override` 的仍是未替换参数的内容，实际加到系统提示词里的还是 `"$ARGUMENTS"`。
3. **thread 里落的是用户原始命令。** session 读取内容、把 `thread.jsonl` 组装进 context 时，最后一条 jsonl 仍是用户的原始命令，而不是被 skill 修改后的命令——因为 thread 落盘发生在 skill 检测之前。这一点弄巧成拙地与上面第 2 条结合，反而让 LLM 知道了用户参数是什么，但那是 LLM 猜出来的。
4. **暴露出的更大问题：context 与 thread 持久化落盘的设计太耦合。** 目前把应该持久化落盘的 raw store 原封不动塞进 ContextManager，处理过于粗放，导致了许多问题。这提醒我们：**保存什么和给 LLM 看什么是两码事**，应该在 session 与 ContextManager 的设计中划分得更清楚一些。

### 2. Subagent

把 subagent 做成 tool、让 agent 自主决定使用，是个很好的思路。目前 agent 对「什么时候使用 subagent、该怎么使用」比较模糊，完全由自己决定——给出自由度不一定是坏事，把 agent 控制得太死也不一定正确。

可以改进的地方：

1. **subagent 的 context 是纯空白**，只有 agent 生成的一句话，可能造成 token 浪费。应该让 agent 传递一些需要的 state 给 subagent。
2. **token / time 控制不足。** 目前 subagent 的 provider 与 agent 完全一样。实际使用中，即使使用了子 agent，token 消耗总量也应该有个度：假设 agent 总共可消耗 10w，分给 subagent1 4w，那其他就只有 6w 可分（当然可以认为涉及 subagent 时 token 总数可以多一些）。此外也应该有 time 限制：subagent 的主要作用是隔离上下文、做一些简单工作，到时间就立刻返回结果，不论正确与否都应返回，让 agent 知道现在的情况——一方面增强 agent 的控制能力，另一方面也让用户更放心。
3. **建议专门增加一个 BudgetManager 类放到 AgentLoop 中**，用于控制循环中的各种临界参数。

### 3. MCP

只用本地 MCP 有点简单，其实应该用 HTTP 接一些外部的真实工具。自己实现一个简单 server、用 TCP + JSON-RPC 通信，从学习角度还可以（但 S0 已经学过），对实际使用帮助不大——目前 MCP 的官方实现已比较成熟，改成那部分更合理。
