今天去海边赶海了回来把kamaclaude的s7部分看完了。这部分确实没有什么特别难以理解的部分。

skill 我的理解 是一种相对固定的工作流 ，可以在工作流中调用tool，甚至其他skill，总之是为了达成某个目的封装好的一套流。这部分实现倒也容易。如果第一个是斜杠，那就在core组建session时，走另外一条路径，读取是否有该skill，读取响应参数，然后在构建agent-loop（主要是context-manager）的过程中，将提前写好的skill.md替换为对应的上下文。将我认为这里的设计如果能通过http协议来快速加载一些skillhub上的skill 那就比较好了。目前skill的加载还是需要用户自己手动添加，其实是比较费事的。

subagent这一块，比较值得说一下。目前是把subagent做成了一个tool，让agent自己决定什么时候调用，什么时候开。实际上，是在agentloop中，使用新的 context ，新的各类参数 新开了一个child-agentloop，创建了新的eventbus，让child-eventbus回传响应event到父eventbus 然后回传给TUI 

MCP这部分 是用了TCP和stdio来做了一个简单的实现，对mcpclient 和mcpserver实现，在本地由mcpserver-manager来对client对 相关server的行为进行管理。

s7其实整体实现比较简陋，有非常多值得修改的地方。

1.首先是skill部分。首先，可以看到skill.md 是替换相关参数后，塞到contextmanager中系统提示词中，这有以下问题，
1）目前是只能接一些纯prompt的skill 一旦某些skill附带某些代码，还是需要依赖llm来自己跑，并不是强制性的
2）目前代码中的实现有一个错误，在session.send_message的实现中 
	goal = self._skill_loader.render_prompt(skill, arguments)
    system_prompt_override = skill.system_prompt_template
而render_prompt函数的实现是return skill.system_prompt_template.replace("$ARGUMENTS", arguments)
由于我们知道python中字符串是不可变的，所以，实际上，这个函数并没有修改skill.system_prompt_template ，所以赋值给system_prompt_override的还是没有替换参数的内容，那么实际添加到系统提示词的system_prompt_override还是"$ARGUMENTS" 
其次，在session读取内容，组装thread.jsonl进context的过程中，我们发现，实际上，最后一条jsonl的数据还是用户的原始命令，而不是被skill修改后的命令，因为thread落盘是skill检测之前就发生的。这一方面 弄巧成拙的和上面2）的问题一结合 让llm反而知道 用户的参数是什么了，但是这是llm猜出来的

但是这其实暴露了了一个很大的问题，目前的架构设计，context和thread持久化落盘的设计太耦合了，直接把应该持久化落盘的raw store 原封不动的塞到context-manager中 ，处理有点过于粗，导致了许多问题。这提醒我们 保存什么和给llm看什么，应该是两码事，应该在session和context-manager的设计中，划分的更清楚一些。

2.subagent这部分 agent把使用subagent作为了一个tool，让agent自主决定使用，这是个很好的思路。目前对于agent来说，什么时候使用subagent，该怎么使用，比较模糊，完全由agent自己决定什么时候使用，这样给定agent自由度，不一定是坏事，因为把agent控制的太死也不一定正确。
不过我认为可以修改的地方在于，
1）目前subagent的context实现是纯空白，只有agent生成的一句话，这可能会导致一些token的浪费，应该让agent传递一些需要的state给subagent
2） 目前subagent的provider和agent是一模一样的，agent对subagent的token，time控制实际上是很不足的。对于实际使用来说，我希望哪怕使用了子agent，token消耗总量也应该有个度，假设agent总共可以消耗10w，分给subagent1 4w 那其他就应该只有6w可以分了（当然可以认为涉及 使用subagent时 token使用总数多一些），此外，对time的限制也应该有，subagent的主要作用就是隔离上下文，做一些简单的工作，限制时间，到了时间就立刻返回结果，不论是正确结果还是 非标准结果，都应该返回来让agent知道现在什么情况，一方面增强agent的控制能力，另一方面也让用户更放心。
针对这一部分，我认为也许 需要 专门增加一个 budget manager的 类 放到agentloop中，由于专门控制循环中的各种临界参数。

3.mcp 单纯觉得目前只用一些本地的mcp有点简单了，其实应该使用http接一些外部的真实工具。自己实现一个简单的server，然后使用tcp 使用jsonrpc来通信，从学习角度来说还可以（但实际上s0已经学过了），对于实际使用帮助不大，因为目前mcp的一些官方实现，也比较成熟，改成这部分更合理一些。
