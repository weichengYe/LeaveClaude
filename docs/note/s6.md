# S6 阶段复盘：上下文工程与压缩的边界

> 对应决策：[ADR 0008](../decisions/0008-s6-context-engineering-review.md)

S6 是上下文的管理，可以看作 S4 的进一步扩展。主要有四块内容。

## 一、三层 context

之前是把 note 全部拼到 system prompt 后面，S6 做了区分：**全局 context、项目 context、session context**，在 runner 中拼进 system prompt。

两点思考：

1. 最小粒度是 session，感觉放到 session-store 中每次更新一次、再由 ContextManager 从 session-store 取并更新会更合理；不过考虑到这里的 context 可能比较大，放在 runner 中每次组合也可以接受。
2. 从我的理解看，全局 context 与项目 context **更应该叫 instruction**——「对未来行为具有规范性约束的、带作用域的规则」，这与我在 S4 中对 state / memory / context 的界定是有区别的。

## 二、tool_result 截断

实现比较简单。唯一需要注意的是返回的是新 list，不改变源对象，因此原始数据中仍然保留全部信息。

## 三、当前上下文占比

实现也简单：计算一下占比，新建一个 event 类，通过 EventBus 发到 client 端，TUI 渲染出来即可。

## 四、自动压缩与手动压缩

**自动压缩**发生在 run 内：读取 thread（假如 150k）→ 发现超过水线则压缩 → 压缩成 5k 形成 summary.md → run 内的消息拼到原始 thread 下，同时拼到新的 summary.md 下并落盘保存 → 因为 compactor 是在 run 下传入的，同一轮 run 使用同一个 summary.md 继续拼接 → 同一 run 内若再次超标，重复上述操作。

**手动压缩**大致类似，区别有两点：

1. 由用户自己在 TUI 填写、点击按钮 → 发送 command → client → server → core → runner 执行压缩；
2. 压缩时直接备份原始 thread，把压缩后的内容作为新的 thread，并把压缩结果通过 EventBus 返回 TUI 供用户了解。

## 五、架构缺陷：自动压缩只在单次 run 内成立

**这是 S6 暴露出的一个架构层面的设计缺陷。** 根源在于 runner 是通过 thread 来获取 session 信息的：

1. 假设当前是 run3，thread 有 150k 需要自动压缩。run3 下正常自动压缩并落盘 summary，之后又在 thread 后拼了 30k；
2. 到了 run4，runner 读取 context 时是**直接从 thread 读取**的，于是直接读到 180k。若认为上下文上限是 200k，run4 仍会压缩并完成本次 run；假设此轮又往 thread 后添加了 30k；
3. 到 run5 时，thread 已超过 200k，发送给 LLM 后会直接报错。

当然可以选择在 run3 结束后手动压缩以避免达到 200k。但如果某一轮 run 比较大，或者用户就是不手动压缩（有用户会认为自动压缩已经生效，而实际上自动压缩只在单次 run 内成立），就会导致某一次 run 在读取 thread 时就已超出上下文——**连压缩的机会都没有**，agent 调用直接失败。

我认为这个设计不合理，因为什么样的用户都有。也许还是应该把某些状态保存在 session-store 中，让 run 可以灵活调用之前 run 的摘要信息（比如只记录最近的一次摘要）。
