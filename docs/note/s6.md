今天再把实际看的s6打一下卡。
这部分是上下文的管理，实际上是之前打卡的s4的进一步扩展。
这一板块的思想和实现也不是很复杂。主要有以下几块：
1. 三层context，之前是把note全部拼到system prompt后面 现在做了一个区分，分为全局context，项目context和session context 。在runner中拼进了system prompt
思考
1）其实感觉有点奇怪，因为这个最小粒度是session，感觉似乎放到session-store中，每次都更新一次，然后context manager从session-store中取并更新似乎合理一些，不过考虑到 这里的context可能有些大，所以放到runner中每次组合也可以
2）从我的理解来看，我认为全局context，项目context 更应该被称为instruction 更合适一些，Instruction差不多是“对未来行为具有规范性约束的、带作用域的规则”的感觉，这和我之前在s4打卡中对state，memory和context的界定还是有一点区别的。

2.tool_result截断，这部分实现比较简单，唯一注意的是，这里返回的是新list 不改变源对象，因此原始数据中还是有全部信息的
3.当前上下文占比，这部分实现也比较简单，简单计算一下，新建一个event类，将其通过event-bus发送到client端，然后tui渲染出来就可以了
4.自动压缩和手动压缩。
这里值得说一下。自动压缩时是在run内的，流程实现是，读取thread (假如150k) -》发现150k 超过水线 压缩-》 压缩成5k 形成summary.md-》run内的消息拼到原始thread下，拼到新的summary.md下 并将其落盘保存 -》因为compactor是在run下传入的，所以同一轮run下使用同样的summary.md并继续拼接-》如果发现同一run下又超了，那就接着上述的操作 
手动压缩，操作大致类似，区别是 1）由用户自己在tui填写，由其tui点击按钮-》发送command-》clinet-》server-》core-》runner 进行压缩 2） 压缩时，直接将原始thread备份，然后将压缩后的作为新的thread 然后 将压缩后的结果通过event-bus再返回到tui下供用户了解

！！！但是自动压缩这里有一个我认为架构上的设计缺陷：由于runner是通过thread 来获取session信息的。
1）我们假设当前是run3 目前的thread 有150k需要自动压缩，那么在run3下会正常自动压缩，并落盘summary，假如后面又继续在thread后拼了30k；
2）但是当进行到run4时，出现了一个尴尬的问题，runner读取context时，是直接从thread中读取的，也就是说 这里会直接读取到context为180k 假如我们认为上下文最大为200k，那么run4还会继续压缩完成本次run，假设此轮run依旧在thread后添加了30k
3）接着继续，在run5的时候，我们发现由于thread超过了200k，发送给LLM后会直接报错

当然我们可以选择在run3结束后手动压缩，让其不会达到200k，但是假如某一轮run比较大，或者用户就是不自己手动压缩（因为可能有用户认为自动压缩也已经达到效果了，实际上自动压缩只在单次run内成立），导致某一次run，直接在读取thread的时候就超出上下文了，连压缩的机会都没有。那agent就调用失败了。

我认为这样的设计是不太合理的，因为什么样的用户都有。也许 还是应该将某些状态保存在session-store中，让run可以灵活调用之前run下的摘要信息（比如只记录最近的一次摘要）
