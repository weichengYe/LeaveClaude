前天晚上看了s2的部分。这一部分算是把deamon和CLI正式连接起来了，之前的调用大模型只是在CLI内部的。
这一部分是把agent的逻辑从CLI中剥离出来，只让core 来负责agent loop的相关部分，同时也算是上两个部分的结合。我理解是 用户输出-》CLI、TUI-》到socket Client -》socket server 接受请求-》runner 负责收到请求后将后续组织起来 包括-》agent-loop -》event-bus 这里event bus是用于将event发送给内部的各个部分，包括内部的event.jsonl writer 也包括 broadcaster -》然后再由broadcaster将相关event发送给订阅给其订阅者如socket Client-》然后CLI、TUI解析从Client中获取的信息资源。这里有这样几个我思考的点。
1.如果把core 看做一个公司的话，event-bus有点类似于公司内部的广播单位，他负责收到各种event后向core内部的各种订阅者发送，broadcaster类似于公司的对外消息发布中心，他本身就是event-bus的订阅者，在收到event-bus的消息后，将event发送给外部订阅者
2.一开始我认为broadcaster向客户端发布event的代码有些问题，因为我看ipc_broadcaster handle函数中用的是逐个向订阅者发送event的设置，当时想如果有多个订阅者，假如有一个订阅者很卡，那可能会导致其他订阅者的收信息很慢。后来我发现，kamaclaude 这种 更像 local claude ，对外部的依赖只有llm api，所以 core和client其实都在本地，那么订阅者其实这里只有client ，那不会存在上述说的问题。不过又进一步思考，如果之后用户是通过b-s架构使用coding-agent 即使用类似 cloud-agent的形式，那可能需要考虑修改。
