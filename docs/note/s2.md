# S2 阶段复盘：core 与 CLI 的正式连接

> 对应决策：[ADR 0004](../decisions/0004-s2-review.md)

## 理解：agent 逻辑从 CLI 剥离到 core

S2 把守护进程与 CLI 正式连起来，并把 agent 逻辑从 CLI 中剥离，只由 core 负责 agent loop 相关部分。数据流：

```text
用户输入 → CLI / TUI → socket client → socket server 接收请求
         → runner 编排 → AgentLoop → EventBus
              ├─ 内部订阅者：event.jsonl writer
              └─ 内部订阅者：broadcaster → 转发给外部订阅者 socket client
                                            → CLI / TUI 解析并渲染
```

## 思考

1. **EventBus 与 Broadcaster 的分工。** 把 core 看成一个公司：EventBus 类似公司内部的广播单位，收到 event 后向 core 内部各订阅者分发；Broadcaster 类似对外的消息发布中心，它本身也是 EventBus 的订阅者，收到消息后再发给外部订阅者。

2. **Broadcaster 逐个发送是否会互相拖累。** 起初认为 `ipc_broadcaster.handle` 逐个向订阅者发送 event 有问题：若某个订阅者很卡，会拖慢其他订阅者。后来判断当前不构成问题——KamaClaude 更接近 local Claude，对外部依赖只有 LLM API，core 与 client 都在本地，实际订阅者只有 client 一个。但若将来以 B/S 架构、类似 cloud-agent 的形态使用 coding agent，这里就需要重新设计。

## 遗留

- 面向多订阅者的 fan-out 与背压处理（见 ADR 0004）。
