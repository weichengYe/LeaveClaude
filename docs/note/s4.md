# S4 阶段复盘：Session 引入与 State / Memory / Context 的边界

> 对应决策：[ADR 0006](../decisions/0006-s4-session-state-memory-context-review.md)

## 一、动机

S3 之后，agent 已能在单次 run 内自主规划、使用各种工具，并有 trace 可以观察。但**不同 run 之间互不互通**。因此需要引入 session 来包含 run，让 agent 在与用户交流时能记得同一 session 下其他 run 的信息。

这实际上是 ContextManager 的职责：合理组装上下文，使 agent 获得应有的 context。

## 二、数据流与实现落点

用户从 CLI / TUI 发送 command → socket client → socket server → core → runner，runner 生成 run_id 后立刻返回。

为了让 core 知道当前 run 属于哪个 session，socket client 发送数据时应带上 session-id；若收到的是 None，则由服务端生成。观察数据流经过的实体，这部分功能适合放在 core 下，新建一个 **SessionManager** 处理与 session 有关的功能，包括但不限于：

- `thread`：之前所有同 session 下 run 的聊天记录
- `note`：agent 自己总结的 session 内容
- 生成 session id、更新 session 下的变量、关闭 session、定义相关数据模型

随后 core 调用 runner 准备开始某一轮 run 时，把根据 session-id 得到的 session 传进 runner，再由 ContextManager 在具体的 AgentLoop 中把 session 属性组装进上下文。

注意：可以把 note 作为一种 event 让 EventBus 广播出去，这样用户可以实时了解 agent 的压缩情况。

## 三、三个实现要点

1. **写入顺序。** 本次 run 会读取整个 thread，因此必须先把本次 run 的信息写入，再启动 run，否则会看不到本次信息。

2. **会话目前有锁。** 下一轮交流必须建立在上轮 run 已结束的前提下。这里有待改进：用户在看见 agent 反馈后，可能希望在 run 结束前重新发送信息进行引导。可考虑：
   - 用户可以在 run 未结束时发送信息给 core；
   - 默认情况下该信息等待上一轮完成，再由 core 组装（既然是引导，也应可取消——TUI 界面提供取消按钮，在组装前取消该任务）；
   - 把是否提前引导交给用户：TUI 中有排队信息，用户可以选择取消、选择等待，也可以直接取消当前 run，把排队中的信息发给 core，让它结合上一轮未跑完的 run 信息开启新一轮 run，从而起到引导作用。

3. **prompt cache 检查点。** 目前似乎没有在上一轮新的 thread 后面加，只在 tools 和 system prompt 之后加了。理解是因为后续要压缩 thread，这部分也会被压缩。

## 四、进一步思考

### 1. state / memory / context 不能混同

S4 把 agent 变成了会话伙伴，一定程度上拥有了记忆，但上下文管理仍然十分简陋，instruction / state / memory / context 的区分还不明显。查阅相关论文与博客后，我的界定是：

- **state**：当前工作的可恢复状态
- **memory**：过去得到的、未来可能再次有价值的经验或知识
- **context**：某一次 LLM inference 实际看到的上下文

对 coding agent 来说，仓库内容本身就是很好的 state 与 state 的出发点：当上下文较长时，从 thread 里查找 Python 版本，不如直接调用工具查看更简单也更正确。此外，coding agent 比一般 agent 更难有稳定且正确的 state 字段；**一些难以从代码中直接恢复的经验，才是有价值的 memory**。

### 2. task 是否该提升到 session 级

S3 让 agent 有了 task 能力，但那是单一 run 下的 task；S4 把 agent 的能力提升到 session 层面，因此考虑过是否把 task 也作为 session 级内容。但同一轮对话中用户的 plan 完全可能变化，草率改成 session 级反而不好；也考虑过在 state 中增加一个 planning 相关字段，目前还不确定。

一个更可行的区分是：

- **work task**：用户真正想做的事，例如「增加 Prompt Cache」「重构 Memory」——可以跨 run
- **execution task**：agent 为完成 work task 或 goal 而拆分的执行性 task——保持在 run 内即可
