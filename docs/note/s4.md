 day6 接着补前两天的卡  这两天看了s4 和s5 。这次卡先补s4。
经过之前的系统设计，agent现在可以在一次run中进行自主规划，并进行各种工具使用，还有trace系统可以用于观察。但是问题在于不同run之间是不互通的。因此需要session的概念，来包含run，让其在和用户交流的过程中可以记得同一session下其他run的信息。
实际上 这是contextmanager的工作，即合理组装上下文 使agent能够获得应该有的context

我们从数据流 从头开始梳理 当用户从CLI/TUI 发送command时，-》socket client  在之前 是使用ipc 将命令发送到socket server 然后server 将相关命令发送给core，core发送给runner,runner生成一个run-id 后立刻返回。 

 为了使core 知道当前run 处于哪个session中，socket client在发送相关数据时应将seesion-id发送过去，如果接受的是none 应该由服务端生成一个。观察数据流经过的实体，可以将这部分功能放在core下。创建一个新类 session manager 用于 处理和session有关的功能，包括但不限于 tread（即之前所有同session下run的所有聊天） 和note（agent自己总结的session下的内容），生成session id，更新session下变量，关闭session，定义有关的数据模型等等

然后在core 调用runner 准备开始某一轮run时 将根据session-id得到的session传进runner  然后由 context manager 在具体的agent loop中将session中的属性组装进上下文。这里注意，可以将note 作为一种event 让event-bus 广播出去 这样 用户可以实时了解相关的agent的压缩情况。

 有几个点。一是由于本次run会读取整个thead 所以 要先将本次run的相关信息写入，再启动run 否则会看不到本次信息。
二是目前会话是有锁的，即下一轮交流应该建立在上一轮run已经结束的情况。其实这里是有待改进的，因为有可能存在 用户在看见agent的反馈时，希望与agent交流，在run结束前，重新发送信息进行引导，也就是说 这里后续可以考虑增加这样一个功能： 1.首先用户可以在run还没结束时发送信息给core2.默认情况下发送的信息可以等待上一轮完成，然后接着由core组装起来（当然由于是引导，也应该可以取消，即在TUI界面中有相关取消按钮 可以在组装之前将这个任务取消掉）3.应该把是否提前引导的功能交给用户，即TUI界面中有一个排队信息，用户可以选择取消，可以选择等待，也可以选择直接取消当前run，将正在排队的信息发送给core，让其结合上一轮没有完全跑完的run的相关信息，进行一轮新的run，从而达到引导的作用
三是a/ 相关的prompt cache 检查点问题，目前似乎没有在上一轮新的thread后面加 只是在tools和system prompt后加了 我理解是 因为后续要压缩thread，这部分也是会压缩的。
看完这一部分后，我有这样一些进一步的思考。
一是，s4的部分将agent变成了一个会话伙伴，一定程度上拥有了记忆。但是感觉目前的上下文管理还是十分简陋，对于instruction，state，memory，context的区分还没有很明显。我查找学习了一些相关的agent memory的论文和博客。这部分实际上非常复杂且值得研究。我认为，state是当前工作的可恢复状态，memory是过去得到的、未来可能再次有价值的经验或知识，context是某一次 LLM inference 实际看到的上下文。几者不能混同。对于coding agent来说，仓库内容本身就是一种很好的state和相关state的出发点。例如，当上下文较长时，从thread中查找 python版本 可能不如直接调用工具查看更简单和正确。此外，coding agent 相比于一些agent 更难有比较稳定且正确的state字段，我认为一些较难以从代码中直接恢复的经验 是比较有价值的memory。
二是，s3使agent有了task的能力，但是 是单一run下的task，本轮将agent的能力增加到了session层面，所以有思考是不是可以将其作为一个session级别的内容，但是后来思考，同一轮对话中，用户的plan完全是有可能变化的，如果草率的将其改为session级的，反而可能不好，早考虑是不是在state中增加一个类似 planning的相关字段，但是目前也不太确定。

但是我认为似乎可以将task区分为work task和excution task 其中 work task是用户真正想做的，比如，增加 Prompt Cache，重构 Memory；excution task是agent为完成work task或goal而拆分的执行性task，其中work task可以是跨run的，而excution task保持在run内即可
