# S3 阶段复盘：Trace 埋点与自主规划

> 对应决策：[ADR 0005](../decisions/0005-s3-review.md)

## 一、Trace

核心原则：**在关键的数据流转点埋点**。如果 S0–S2 学得比较清楚、能自己画出数据流图，就很自然地知道该在哪里改代码。定义好 `TraceRecord` / `TraceWriter` 之后，把 trace 作为属性挂到 Runner、SocketServer 等实体上，运行过程中记录即可。

三个值得注意的设计点：

1. **埋点不能阻塞原有流程。** 为避免影响 IPC、AgentLoop 等原有进程，先写入内存队列，再由后台异步任务逐个落盘。
2. **所有 run 的 trace 写同一个文件，读取时再区分。** trace 的用途是了解 agent 的整体情况，而不是某一次 run（那是本地 `event.jsonl` 的职责）。调试跨 run 的全局问题——例如多个 run 竞态导致某些 run 很慢——时，全局文件比单个 run 文件更容易发现问题。
3. **`LLMTokenEvent` 的 trace 用 wrapper 实现。** 在 provider 外面再包一层，既保护 provider，也便于替换 provider 而不必改动其他部分。

## 二、自主规划

KamaClaude 把 plan 做成 tool（`task-create` / `update` / `list` / `get`），让模型自行分析是否需要创建计划，并用 DAG 控制依赖。

### 实测发现

给了一个真实任务：

> 当前项目新增一个 `kama run --file <path>` 功能：允许用户从文本文件读取 goal 并发起 Agent Run。请先检查现有 CLI、配置和 run 命令实现，设计修改方案；然后实现参数解析、文件读取、错误处理，并补充对应测试，最后运行完整测试验证。

结果：受 `max_steps` / `max_tokens` 以及部分工具使用限制的影响，模型改完 `kama run` 的命令行参数后就停止了。改动已经落盘，原有命令不可用——需要三个命令行参数才能跑通。

### 改进方向

这属于工具安全使用 / harness 层面的问题。类比数据库，这类操作应当具备 ACID 的部分特性，让 agent 出错后能够：

1. **回到原状态**——checkpoint 机制；
2. 除了全程 trace 之外，还应当说明：这次出错还可能有什么 bug、如果有 bug 该怎么改；
3. 给出后续如何避免同类问题的结论。

（这里的 bug 不限于代码错误，也包括决策错误。）

否则 agent 可能陷入反复出错的循环。

## 遗留
