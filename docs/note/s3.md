还是来补昨天的打卡。昨天把kamaclaude 中s3 trace和自主规划的部分看完了。
其实这一部分相比前面来说相对要简单一些。
首先是trace部分，我认为如果前面s0-s2学的比较清楚，对数据在各个实体之间的流转有一个相对比较清楚的认识，自己能画出来数据流图的话，可以比较自然的知道该从哪里进行代码修改。主要原则就是在一些关键的数据流转过程进行trace。在这一部分将tracerecord tracewriter 这样的类定义好之后，很自然的将trace放到runner，socket server等实体下面作为一个属性，然后再运行的过程中埋点记录即可。

这里有几个值得注意的点。1.为了防止埋点影响原有实体的原有进程，比如进行ipc，agent loop，可以先将其读到队列中，内存中，由后台的异步进程逐个写入文件。2.在写入时将所有run的trace都写到一个文件中，在读的时候进行区分，这是因为trace的主要功能是用来了解agent的情况，而不是具体到某次run（这是本地的event.jsonl的作用），这样做的好处很明显，当需要调试一些涉及agent全局的情况（比如多个run竞态发生，导致某些run很慢时），全局文件比较好发现问题，而单个run文件很难发现。3.在对llmtokenevent进行trace时，可以采用wrapper的方式，再provider外面在包一层，保护provider，这样做的好处是可以比较方便的替换provider，而不考虑其他。
然后是自主规划plan 这里， kamaclaude这里是将plan做成了tool 即 task-create/update/list/get，让模型自行分析选择是否需要创建计划，同时使用DAG来控制依赖。
我这里实际测试的时候发现这样一些问题：我给了如下的命令让其做：
“当前项目新增一个 kama run --file <path> 功能：允许用户从文本文件读取 goal 并发起 Agent Run。请先检查现有 CLI、配置和 run 命令实现，设计修改方案；然后实现参数解析、文件读取、错误处理，并补充对应测试，最后运行完整测试验证.”
但是我发现由于max_step和max_token 和一些工具使用的限制，他自行把 kama run的命令行参数改完之后就停止了，这导致我重新再使用的时候发现需要三个命令行参数，我原来的命令跑不了了。我认为这涉及到kamaclaude 中对工具安全使用，harness相关的部分。由于之前学数据库，我在想 似乎这些操作在某种程度上也应该拥有ACID的一些特性，在agent出现问题报错后，通过事务设计或者文档设计或者预期结果设计的方式，让agent出错后可以1.回到原来的状态 即checkpoint机制 2.不仅有文档记录全程trace，应该1）让我知道这次出错还有可能有什么bug，2）如果有bug我需要怎么改 3.后续怎么做才能避免这些bug  （bug不止是代码错误 也包括一些涉及错误）。
否则我认为agent可能会陷入一直错误打转的循环。
